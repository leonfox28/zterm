# 设备授权撤销语义

## 风险

zterm 的长期设备公钥相当于该宿主当前 OS 用户的远程 Shell 凭证。若手机或笔记本遗失，仅从授权列表删除公钥但保留已经建立的 Iroh connection，会产生明显漏洞：攻击者可以维持现有连接、继续打开 session stream、接收输出或输入命令，直到连接自然断开。

因此“拒绝未来握手”不等于完成撤销。撤销必须覆盖该设备当前及未来的所有访问路径。

## 建议语义

宿主执行 `zterm revoke <device>` 时应按以下顺序处理：

1. 先把授权删除或授权 epoch 变化持久化到本地存储；持久化成功才继续，避免 daemon 崩溃后授权复活。
2. 标记该公钥已失效，使所有新 RPC、stream 和重连立即被拒绝。
3. 查找该公钥对应的全部活动 Iroh connection，包括重连竞争期间可能短暂并存的旧/新连接，并以明确的 `authorization_revoked` 原因关闭。
4. 取消该设备的所有 attachment，释放对应 session 的 controller lease，停止向其发送终端和轻量事件。
5. 保留 PTY、根 Shell、Agent 和其他 session 资源继续运行；撤销设备访问与终止用户任务是两种独立的破坏性操作。

为了防止 connection 已开始 dispatch 的请求越过撤销边界，授权检查不能只发生在最初握手。连接/attachment 应携带授权 generation 或 cancellation token；撤销后尚未提交的输入和新 stream 必须失败。已经到达 PTY 的命令无法撤回，这是所有远程终端撤销的现实边界。

## UX 与范围

- CLI 应显示目标设备名、公钥短 ID、最后连接时间及当前 attachment 数量，防止撤销错设备。
- 若目标在线，提示会立即中断其控制连接，但不会杀死远端任务。
- 操作可以要求交互确认并提供显式非交互参数；安全紧急场景不能要求访问被撤销设备。
- 当前项目没有中央账号或全局控制面，因此撤销只作用于执行命令的这一台宿主；用户仍需在其他曾授权该设备的宿主上分别撤销。
- 以后重新授权同一物理设备必须重新完成一次性票据配对。是否复用原设备公钥不改变撤销的本地原子性要求。

## 取舍

立即关闭现有连接可能中断用户正在进行的合法操作，但不会终止 PTY，其他授权设备可以马上 reattach。若只对未来连接生效，遗失设备可无限延长现有 QUIC connection，无法满足撤销作为安全控制的基本预期。因此建议采用立即生效模型。
